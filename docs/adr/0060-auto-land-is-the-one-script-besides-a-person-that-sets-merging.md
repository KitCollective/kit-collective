# Auto-land is the one script besides a person that sets Merging

Nicklas, 2026-10-12. Status: accepted. Supersedes only the clause of ADR-0057 that says a person moves the issue to `Merging` (the table row "Merging: approved", the "owner's only moves" sentence, and "Why Merging stays" where it says the approver's move is the signal). Everything else in ADR-0057 stands: `Merging` is still the only merge permission (`MERGE_PERMISSION_STATUS` in `scripts/lib/land-policy.mjs`, unchanged in meaning), and `Approval` still means a human must act.

## Why

After ADR-0058 the `kit-issue` workflow takes an issue from `To-do` to `Approval` unaided, and a person says "approve" for every merge. The owner wants AFK sessions in which a person is not part of the normal case. `Approval` becomes the emergency exit: a rule was exceeded, or a human is genuinely needed. It is no longer a per-merge step.

## Decision

1. **Who may set `Merging`**: a person, or `scripts/auto-land.mjs` under the conditions below. Nothing else: not the workflow, not an agent thread, not Linear automation. The workflow still has no `Merging`, `Post-Merge` or `Done` in `MAY_SET`, still never posts a receipt for real and never names `gh pr merge`.
2. **Enforcement lives inside the acting script, never in a relayed result.** ADR-0058 records that gate results reach the workflow through a Haiku runner model that relays exit codes, so they are not merge-grade. `auto-land.mjs start` therefore re-reads everything from GitHub, git, Linear and the run log itself, right before it enqueues, and refuses (exit 1, one `REFUSED (auto-land): <code>: <detail>` line) if any check fails. A runner that lies or is sloppy can start the script, or not; it cannot make an unsafe merge happen. The script runs the existing scripts (`audit-receipt.mjs`, `gate.mjs review`, `merge-lock.mjs`) as child processes and goes by their exit codes in its own process; it reuses `landAtMergeGate` for the merge arguments and the required-check test.
3. **`start <pr> --issue KIT-n [--dry-run] [--force-enabled] [--handoff]`** checks, in this order, stopping at the first failure:
   - (a) the kill switch is off (below) and the circuit breaker is closed (below);
   - (b) the PR is open, not a draft, into the lane, `MERGEABLE`, at the checkout's HEAD (by SHA), the checkout is clean, no auto-merge is already on;
   - (c) the issue is `In Review` (never `Approval`), carries none of `signal-up`, `wontfix`, `needs-info`, `ready-for-human`, and has no unresolved `blockedBy`;
   - (d) risk class: `startDecision` says high-risk (schema, auth, IAP, workflows) or the diff touches a high-risk or factory path, or the issue is `surface:mobile` without `no-device-needed`, or the diff has more than 400 changed lines, or any file is outside the issue's own `write-scope:` (no scope declared also refuses). High risk is always `needs-human`;
   - (e) the run log shows an independent reviewer (a `spawn reviewer` with thread, provider and model, none of the issue's engineer spawns on the same provider and model) and the `kc/audit` receipt for exactly this head is posted: when the status is not yet success the script posts it by running `audit-receipt.mjs post` with `--require-different-model`, which keeps its own provenance checks (nothing weakened), and then requires a green `audit` event for the head in the run log;
   - (f) `gate.mjs review` run here, within the 480 s total budget of one call (60 s are kept back for the steps after it); exit 3 is returned as waiting;
   - (g) the runaway ceiling: fewer than `flow.autoLand.maxPerDay` (default 100, constant `DEFAULT_MAX_PER_DAY` in `scripts/lib/auto-land.mjs`) `auto-land` start events in the run log in the last 24 hours; checked again under the lock. It is a runaway guard, not a throttle;
   - (h) only then: take the merge lock (a second `start` waits for it), fetch the lane again and trial-merge it into the head (`git merge-tree --write-tree`, nothing in the worktree, index or remote changes; a conflict releases the lock and refuses `conflict`), check that the PR head still equals the audited head (a push refuses `head-mismatch`), log the `start` event (a failed log write aborts before anything is changed), set `Merging` with one comment `Auto-approved: <the conditions that held>`, enqueue with `gh pr merge <pr> --merge --auto`.

   `--dry-run` runs every check and prints the verdict and changes nothing: no receipt, no lock, no Linear write, no enqueue, no run-log line (`KC_DRY_RUN=1` also stops `gate.mjs` from logging). It posts no receipt, so when `kc/audit` is a required check the gate can say waiting in a dry run. `--handoff` (the workflow passes it) makes a refusal also move the issue to `Approval` with `ready-for-human` and comment the reason.
4. **`finish <pr> --issue KIT-n [--timeout s]`** waits in slices (exit 3 = still waiting, as `gate.mjs`) until the PR is `MERGED`, sets `Post-Merge`, runs `gate.mjs land` itself, then comments the merge SHA, sets `Done`, releases the lock and deletes the merged remote branch (the local worktree is for `reap-worktree`). It refuses unless the issue is `Merging` or `Post-Merge` and the run log holds an auto-land start for it. **The alarm**: a PR the queue dropped (closed, or open with auto-merge off and not in the queue on two polls in a row), a red integration check on the merge commit, a failed enqueue, or any failed write after `Merging` was set, releases the lock, swaps the Triage label to `ready-for-human`, moves the issue to `Approval`, comments the cause and logs `auto-land alarm` with a reason code. That is the signal for a person.
5. **Opt-in, shipped off.** `flow.autoLand.enabled` is `false` in `factory.config.json`. The workflow input `autoLand` (boolean, default false) turns it on for one run (the workflow passes `--force-enabled`); without it the workflow asks `auto-land.mjs enabled` and only the exact line `AUTO-LAND ON` counts. With it off the workflow stops at `Approval` exactly as before. With it on and a refusal, the workflow leaves the issue in `Approval` with `ready-for-human`; it never stops silently in `In Review` (it does so only for a waiting verdict that never finished, and for an unreadable result).
6. **Kill switch**, any one of: the label `hold` on the issue; the file `.factory/auto-land.off` in the main checkout (`touch .factory/auto-land.off` to stop, delete it to allow; the file wins over `--force-enabled`); `flow.autoLand.enabled` false without `--force-enabled`. The config is read from the main checkout, never from the PR's own copy, so a PR cannot enable it for itself; `factory.config.json` and the factory's own enforcement scripts are in the high-risk set, so a PR that edits them is never auto-landed.
7. **The circuit breaker is the real brake.** `start` reads the run log: if the last `flow.autoLand.breakerAfter` (default 3) `auto-land` outcomes are all `alarm` (an ejected PR, red integration CI after merge, a failed enqueue: the cases where a person was asked), it refuses with `breaker-open`. A `landed` outcome resets the count. A person clears it, after the cause is fixed, with `node scripts/auto-land.mjs reset`, which only writes a `breaker-reset` event to the run log; every alarm comment names that command.
8. **Throughput is serialised by construction.** The merge lock is taken in `start` just before the trial merge and enqueue and released in `finish` (or on any refusal or alarm), so exactly one PR is between enqueue and landed at a time. A second `start` for another PR waits for the lock inside its 480 s budget (exit 3, waiting, if the budget runs out; the workflow repeats the slice) instead of failing, so many PRs queue up and land one after another. Each PR syncs with the lane, gets its own checks and its own audit. Estimate: roughly one PR per merge-queue round trip plus the integration check, a few minutes each, so on the order of 10 to 20 PRs per hour at best; the owner can judge whether that is enough.
9. **Agents may not merge by any other route.** The skills `issue-session`, `bb-orchestrate`, `land` and `implement` and `docs/agents/bb-harness.md` say: `Approval` is the exception exit; the normal path ends at `Done` through auto-land when it is enabled; the human path (a person moves the issue to `Merging`, then `/land`) is unchanged.

## Why a branch behind the lane is fine, and the audit stays valid

Many PRs land per day and a run takes tens of minutes, so the lane has almost always moved by the time `start` runs; requiring the branch to hold the lane (or syncing it) would refuse nearly everything. `start` therefore does not sync and never changes the head. The receipt binds to the PR head the reviewer judged, and that head is exactly what is enqueued (it is checked again under the lock). The merge queue then integrates it with the newest base and the combined state is tested by the queue's own CI (`merge_group` in `ci.yml`); a semantic clash with newer code is what that run is for, and a red run is the `queue-ejected` alarm of `finish`. Only a textual conflict is refused up front, by the trial merge, because the queue would eject it anyway.

## What is and is not verified

Verified by tests (`scripts/tests/auto-land.test.mjs`, `scripts/tests/kit-issue-workflow.test.mjs`): every refusal condition above, one per case, against a scratch git repo with a bare origin, a fake `gh`, a fake `bb`, a fake Linear CLI and a fake gate, with the real merge lock, git trial merge, audit receipt and run log; the happy path through the enqueue; that `--dry-run` writes nothing; `finish` success and each alarm; the workflow with autoLand off, on, refused, waiting and with a silent runner.

**Not verified:** any run against real bb threads, real Linear, real GitHub or a real merge queue. In particular: `bb workflows validate` (needs a bb project thread; run it after merge), that a real `gh pr view` reports `isInMergeQueue` and `autoMergeRequest` the way the ejection test assumes (the ejection rule needs two consecutive polls with both off), that the Linear labels `hold` and `no-device-needed` exist (they are in `factory.config.json` and need the bootstrap skill to create them), and that GitHub's merge queue enqueues on `gh pr merge --merge --auto` for a PR that is already green (the existing land path assumes it).

## Before first use

`auto-land start` posts the real `kc/audit` status from the machine's own `GH_TOKEN`, which needs "Commit statuses: Read and write" (fine-grained) or `repo:status`. A token with Read only ends in `UNKNOWN (receipt): token lacks Commit statuses write`; the owner raises it before the first real use. `bb workflows validate` must also be re-run in a bb thread, and the labels `hold` and `no-device-needed` created in Linear.

## Decision needed

1. **`surface:mobile` default**: refused unless `no-device-needed` (the container has no simulator). Relax it per issue with the label, or globally in `riskClass`.
2. **The 400-line cap** (`MAX_DIFF_LINES`); a binary file counts as 400.
3. **The ceiling of 100 starts per day** (`flow.autoLand.maxPerDay`) and **the breaker after 3 consecutive failures** (`flow.autoLand.breakerAfter`). Both are the owner's to tune.
4. **Strictness beyond the brief**: `needs-info` and `ready-for-human` also stop auto-land; a diff touching `.bb/**`, `.github/**`, `factory.config.json` or the enforcement scripts is `needs-human`; an issue with no `write-scope:` is refused.
5. **The first live trial**: one small, single-area, non-mobile issue (docs or a script test), started with `autoLand: true` after `--dry-run` on its PR, with a person watching the Linear board and ready to `touch .factory/auto-land.off`.
