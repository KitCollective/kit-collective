# Device flows on the iOS Simulator are the evidence for mobile slices

Nothing tested the app end to end on a device, and evidence on issues was "after" only, taken from a headless browser on the web target, so a reviewer could not see what a change did to a real screen and an agent could change design nobody asked for without it showing. Five **Device flows** (Maestro, under `apps/mobile/.maestro/flows/`) now run on an iOS Simulator build for every slice that touches `apps/mobile/**`, and on `development` after such a slice lands. The decisions are Nicklas's from KIT-267 (2026-10-07):

- **Where it runs:** on the approver's Mac, started by the `/issue-session` that implements the slice (`apps/mobile/.maestro/run-evidence.sh`). The first decision was EAS Workflows with the `maestro` job; EAS refuses that job without a paid plan, and Nicklas chose local runs over the plan the same day. The runner leans on the Mac for the simulator (`xcrun simctl`), the `gh` login and the Claude subscription; the comparison, upload and report scripts are plain Node and would move to a hosted runner unchanged.
- **Platform:** iOS Simulator only. No Android, no physical device, no camera branch.
- **Backend:** a local API on a disposable database with the fixture catalog. The first decision was the `staging` lane API; with local runs a local API needs no lane secret, cannot write to a lane, and cannot show another Collector. The same test-data routine can be run against a staging database as a shell command (`E2E_TEST_DATA_TARGET=staging`); the API route cannot, see decision 2.
- **Blocking:** a red flow blocks, through the `Device flows` commit status the run sets on the PR head. The issue asked for a required check; the status is not added to the `lane-development` ruleset (which requires a pull request and `test`), because a required status cannot be limited to mobile PRs and would block every other PR, so the checker enforces it: a mobile PR whose head has no green status fails review. A **Design finding** from the review is advisory: it is reported and never fails the status.
- **Storage:** screenshots and recordings go to an evidence bucket of their own (`kc-e2e-evidence`) under `e2e/<sha>/<flow>/`, with a 30-day lifecycle. Not in git. The first decision was lane R2 under an `e2e/` prefix; see decision 4.

Five things were decided while building it, because the first decisions did not settle them:

1. **Two test Collectors, not one.** The paywall Sheet only shows to a Collector with no live Entitlement and a spent trial, and Tilføj trøje needs access. The **Test Collector** (Comp Entitlement) signs in for four flows; the second test Collector, who also owns the åben-for-bud UserJersey, signs in for the Ønske and paywall flow.
2. **The test data is reset before every flow, through the API.** Flows change data (Tilføj adds a UserJersey, Send bud leaves a bid), so two runs of one commit only compare as `same` when each starts from the same rows. `POST /v1/e2e/test-data` runs the same idempotent routine as the `e2e:test-data` command. It answers 404 on any API that does not set `E2E_TEST_DATA_TOKEN`, needs that token as a bearer, answers 404 on a process with `NODE_ENV=production` whatever else is set, refuses `E2E_TEST_DATA_TARGET=production` and a `DATABASE_URL` that equals `PRODUCTION_DATABASE_URL`, and writes only rows owned by, or pointing at, the two test Collectors. Lane database URLs carry no lane marker (an IP and one database name), so a URL alone cannot prove it is not production; that is why the target must be declared and why the production process refuses by itself. The API image sets `NODE_ENV=production` for staging too, so on a deployed API the route and fixed Vision are off everywhere today.
3. **Fixed Vision is scoped by Collector, not by lane.** With `VISION_FIXED_FOR_TEST_COLLECTOR=on` the test Collector's Vision jobs go to a fixed adapter that returns one suggestion from the catalog at hand; every other Collector, and unsigned Vision, stays on the live adapter. There is no switch that changes Vision for real Collectors, and a process with `NODE_ENV=production` ignores this one.
4. **Evidence lives in a public bucket of its own, never a lane bucket.** A PR comment and a Linear issue need links that open without a session for 30 days; a presigned R2 URL lasts 7 at most, and making a lane bucket public would expose every Collector's photos. No `development` lane API exists to serve the bytes either (Coolify runs staging and production only). Nicklas created `kc-e2e-evidence` with a public r2.dev address on 2026-10-08. It holds only `e2e/` objects, which show the test Collectors and drawn shirts; the scripts refuse to run without `E2E_R2_BUCKET`, so evidence cannot land in a lane bucket by default. This is an exception to the object-storage lock (one bucket per lane, signed GETs), which covers Collector and catalog photos.
5. **The run is tied to the commit it is keyed by.** `build-local.sh` and `local-api.sh` stamp what they built with a hash of the tracked sources; `run-evidence.sh` refuses to run when the app on the simulator or the local API was built from other sources than HEAD, so a commit cannot get a green status from screenshots of an older build.

"Before" for a PR is the latest passed `development` run at or before the PR's merge base; "after" is the PR head. The comparison is a pixel difference with a small tolerance and no model call; the iOS status bar strip is not compared. Only steps marked `changed`, `new` or `removed` go to the review, which gets the pair, the issue's What to build and write-scope, and the matching sections of `docs/design-system.md`. A changed screen the issue did not ask for is a finding by itself. The reviewer flags; it never edits UI. It is a headless Claude Code run (`claude -p`) on the approver's Claude subscription with the Read tool only (Nicklas, 2026-10-08, instead of a model API key of its own); environment API keys are removed from the run so it cannot bill an API account.

The first-session flow covers what a Collector can reach today (splash, onboard, door, Samling). Showcase and first photos are in the code but unreachable from a cold start, so no flow covers them.

Status: accepted.
