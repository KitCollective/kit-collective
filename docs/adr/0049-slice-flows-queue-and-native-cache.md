# A slice proves itself with its own Device flow; the five flows are regression, and builds queue and reuse the native binary

Supersedes parts of ADR-0048. Nicklas, 2026-10-10, after KIT-272, KIT-279 and KIT-280 stood in `Implementing` with finished code and green CI, each waiting for its own full Xcode build on one Mac that had 117 MB of free disk and a load average above 250.

What ADR-0048 got right stays: iOS Simulator, a local API on a disposable database, fixed Vision for the **Test Collector**, evidence in `kc-e2e-evidence`, the `Device flows` commit status enforced by the checker, a **Design finding** that is advisory. What changes:

1. **A slice runs its own flow, not the five.** The evidence for an issue is `apps/mobile/.maestro/slices/<KEY>.yaml`, written by the implementer in the same PR: one screenshot per Acceptance criterion that a screen can show, and nothing else. The five flows (first session, Tilføj trøje, Samling, Søg and bud, Ønske and paywall) move to `apps/mobile/.maestro/regression/` and run only on request (`E2E_FLOWS=regression`): at a milestone, before a promotion to `staging`, or when a slice changes something several screens share. They are not deleted; they are no longer the gate.
2. **No "before" is required.** A slice flow has no earlier run, so its steps are `new` and the review judges them against the issue and `docs/design-system.md`. The comparison against a `development` run still works when a regression run exists, but `/land` no longer owes a run on the integration lane after every mobile slice. What this gives up: the pixel check that a slice changed nothing it was not asked to. A slice that edits a shared component has to say so in its flow or run the regression flows.
3. **The checker judges the flow too.** The implementer writes the flow that proves their own slice, so the fresh review reads `slices/<KEY>.yaml` against the Acceptance criteria: a criterion a screen could show with no step behind it is a Spec finding, as is a step that proves nothing (it screenshots a screen the slice did not change).
4. **Device work is a queue.** The flows share one simulator, port 3000 and one database that `local-api.sh` drops, so two sessions cannot run at once. `apps/mobile/.maestro/device-run.sh` takes a lock in the clone's common git directory, runs the API, installs the app, runs the flow, publishes the evidence, stops the API and releases the lock. A lock whose owner has stopped is taken over. `/issue-session` runs it as one command; it never starts `local-api.sh`, `build-local.sh` or `run-evidence.sh` by hand.
5. **The native binary is built once.** A Release app is a native binary plus one Hermes bytecode file. The binary is cached under a hash of what the native build reads (the lockfile, `patches`, `apps/mobile/package.json`, `app.json`, `app.config.js`, Xcode's version) in `~/.cache/kit-e2e/native`, shared by every worktree, the newest two kept. On a hit `build-local.sh` bundles the JavaScript with `expo export:embed`, compiles it with the `hermesc` of the pinned `hermes-compiler`, swaps it into a copy of the cached app, signs it ad hoc and installs it. A full Xcode build runs only when the hash changed, and refuses to start under 12 GB free.

Tried while deciding: bundling and compiling the real app's JavaScript with the pinned toolchain gives bytecode version 98, the version of the installed Release app, with the same assets layout. Not tried: a hash that ignores JavaScript-only dependency changes in the lockfile; the lockfile stays coarse so a stale binary is never paired with new native code.

Status: accepted. Supersedes in ADR-0048: "Five Device flows … run … for every slice", the `development` run after landing, and the three-command run.
